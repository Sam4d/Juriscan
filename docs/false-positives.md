# False positives and false negatives

Treat findings as reviewable evidence. Check the exact path/line, detector limitations, deployed behavior and business facts. Public database rows and intentionally public Firebase reads can match high-severity technical patterns without exposing private data. A server middleware may validate a webhook signature outside the inspected function. Components may supply accessible names or alternative text at runtime. Static imports do not establish tracking execution.

For reproducible feedback, provide a minimal synthetic source sample, detector/version, expected versus observed result, and relevant framework details. Do not post credentials, customer source, personal data or private findings. The fixtures under `test/` document current expected triggers/non-triggers; they are not comprehensive real-world accuracy measurements.

No persistent suppression format is implemented. The core/MCP supports explicit `include_rules`; selected IDs appear in scan manifests, so exclusions are visible. Do not hide findings by silently modifying detectors or calling omitted checks “passed.” CI's default gate is none; only explicitly selected confirmed syntactic severities gate. Retain an external review record with rationale, owner and expiry for accepted risk until a reviewed suppression workflow exists.
